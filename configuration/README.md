# Configuration Management

Ansible takes three **blank servers** and turns them into two web servers and one database server, all from one playbook. Then you change things, break things, and watch Ansible fix them.

## What is configuration management?

**Setting up the inside of a server**: installing packages, creating users, writing config files, starting services.

|               | Provisioning (`provisioning/`)       | Configuration management (this)            |
|---------------|--------------------------------------|--------------------------------------------|
| Question      | *Does the server exist?*             | *What's installed and running on it?*      |
| Restaurant    | Build the room, tables, chairs       | Stock the kitchen, train the staff         |
| Typical tools | Terraform, OpenTofu, Pulumi          | Ansible, Chef, Puppet, SaltStack           |

Without a tool, you SSH into each server and type `apt install ...`, edit files by hand, and hope all 20 servers end up the same. With Ansible you write the **desired result** once, and it SSHes into every server and makes it true.

## The idea: one control node, many servers

```
                          SSH   ┌── web1  (webservers) ── nginx ── localhost:8091
control  ── ansible-playbook ───┼── web2  (webservers) ── nginx ── localhost:8092
(Ansible lives here only)       └── db1   (dbservers)  ── redis
```

| In real life                         | In the demo                                       |
|--------------------------------------|---------------------------------------------------|
| Your laptop with Ansible installed   | `control` container                               |
| Fresh cloud VMs / physical servers   | `web1`, `web2`, `db1` (only SSH + Python inside)  |
| Your SSH key on the servers          | Key pair generated by `control`, shared via a volume |
| Server IPs                           | Container names, resolved by Docker DNS           |

**Agentless**: nothing Ansible-specific is installed on the servers. Ansible only needs SSH and Python there.

## Walkthrough

Requirements: Docker with Docker Compose v2.

### Step 1: Start the control node and three blank servers

```bash
cd configuration/demo
docker compose up -d --build
```

The servers are empty. There's no web server yet:

```bash
curl localhost:8091                       # fails: connection refused/reset
docker compose exec web1 which nginx      # nothing
```

### Step 2: Open a shell on the control node

```bash
docker compose exec control bash
```

All the following `ansible` commands run **inside** this shell, in `/ansible`.

### Step 3: Can Ansible reach the servers?

```bash
ansible all -m ping
```

```
web1 | SUCCESS => { "ping": "pong" }
web2 | SUCCESS => { "ping": "pong" }
db1  | SUCCESS => { "ping": "pong" }
```

These are **ad-hoc commands**: one-off actions without a playbook.

```bash
ansible webservers -a "hostname"         # run a command on a group
ansible db1 -m setup -a "filter=ansible_distribution*"   # facts Ansible collects
```

### Step 4: Preview, then run the playbook

`--check` is a dry run (like `terraform plan`), and `--diff` shows what would change inside files:

```bash
ansible-playbook site.yml --check --diff
```

Some tasks may fail in check mode on a blank server (e.g. "start nginx" before nginx is installed). That's expected, because nothing was really installed.

Now do it for real:

```bash
ansible-playbook site.yml
```

```
PLAY [Common setup for every server] ****
TASK [Install common packages]   changed: [web1] changed: [web2] changed: [db1]
TASK [Create admin users]        changed: [web1] => (item=alice) ...
PLAY [Web servers] ****
TASK [Install nginx]             changed: [web1] changed: [web2]
...
RUNNING HANDLER [Reload nginx]   changed: [web1] changed: [web2]
PLAY RECAP ****
db1   : ok=8  changed=5  failed=0
web1  : ok=9  changed=6  failed=0
web2  : ok=9  changed=6  failed=0
```

(Numbers will vary slightly.) From your normal terminal, outside the container:

```bash
curl localhost:8091          # Sweet Bakery ... Served by web1
curl localhost:8092          # Sweet Bakery ... Served by web2
curl -sI localhost:8091 | grep X-Served-By
docker compose exec db1 redis-cli ping           # PONG
docker compose exec web1 id alice                # alice is in group sudo
```

### Step 5: Run it again, and nothing changes

```bash
ansible-playbook site.yml
```

```
db1   : ok=7  changed=0  failed=0
web1  : ok=8  changed=0  failed=0
web2  : ok=8  changed=0  failed=0
```

Every task said `ok`, which means *already correct, did nothing*. That's **idempotency**: tasks describe a **state** (`state: present`), not an action, so running them repeatedly is safe.

### Step 6: Drift. Someone breaks a server by hand

From your normal terminal:

```bash
docker compose exec web1 rm /var/www/html/index.html
docker compose exec web1 userdel bob
curl localhost:8091          # 403 Forbidden, the page is gone
```

Back in the control shell:

```bash
ansible-playbook site.yml
```

Only **web1** shows `changed` (page restored, bob recreated). web2 and db1 stay `ok`. Ansible fixes only what drifted.

### Step 7: A change request: "We open at 7am now!"

Edit `demo/ansible/group_vars/webservers.yml` (from your editor; it's mounted into the container):

```yaml
site_message: Open 7am - 5pm
```

Preview, then apply:

```bash
ansible-playbook site.yml --check --diff     # shows -8am / +7am for web1 and web2
ansible-playbook site.yml
curl localhost:8092                          # (outside) Open 7am - 5pm
```

Only `Deploy home page` changed. The nginx config didn't change, so the **handler did not run**, and nginx wasn't reloaded for nothing.

### Step 8: Target a subset

```bash
ansible-playbook site.yml --limit web2       # only web2
ansible-playbook site.yml --limit dbservers  # only the db group
```

Clean up (outside the container):

```bash
docker compose down -v      # -v also removes the SSH key volume
```

## What's in the demo

```
demo/
├── docker-compose.yml           # control + web1 + web2 + db1
├── control/                     # image with Ansible; creates the SSH key pair
├── server/                      # "blank server" image: Debian + SSH + Python + sudo
└── ansible/
    ├── ansible.cfg              # defaults: inventory, SSH user, key
    ├── inventory.ini            # WHICH servers, in groups
    ├── site.yml                 # the playbook: WHAT each group should look like
    ├── group_vars/
    │   ├── all.yml              # variables for every server (users, packages)
    │   └── webservers.yml       # variables for web servers (page text)
    └── templates/
        ├── index.html.j2        # home page, filled in per server
        └── nginx-site.conf.j2   # nginx config, filled in per server
```

## Key concepts

| Term          | Meaning                                                      | In the demo                          |
|---------------|--------------------------------------------------------------|--------------------------------------|
| Control node  | The machine that runs Ansible                                | `control`                            |
| Managed nodes | The servers Ansible configures                               | `web1`, `web2`, `db1`                |
| Inventory     | List of servers, grouped                                     | `inventory.ini`                      |
| Playbook      | YAML file of plays                                           | `site.yml`                           |
| Play          | "On these hosts, do these tasks"                             | `Web servers`, `Database servers`    |
| Task          | One desired state, using one module                          | `Install nginx`                      |
| Module        | The built-in tool a task uses                                | `apt`, `user`, `template`, `service`, `lineinfile` |
| Variables     | Values that differ per group/host                            | `group_vars/*.yml`                   |
| Template      | A file with `{{ placeholders }}` (Jinja2)                    | `templates/*.j2`                     |
| Handler       | A task that runs only when notified by a change              | `Reload nginx`, `Restart redis`      |
| Facts         | Info Ansible gathers about each server (OS, IPs, ...)        | `ansible db1 -m setup`               |
| `become`      | Run with sudo                                                | `become: true`                       |

## Notes and gotchas

### Prefer modules over `shell`

```yaml
# ❌ Runs every time, always reports "changed", breaks on the 2nd run
- ansible.builtin.shell: useradd alice

# ✅ Checks first, only acts if needed
- ansible.builtin.user:
    name: alice
```

`shell` and `command` are an escape hatch. Modules give you idempotency for free.

### Handlers run once, at the end of the play

If 3 tasks notify `Reload nginx`, nginx is reloaded **once**, after all tasks in the play. If the playbook fails before then, the handler doesn't run.

### Containers are not quite real servers

These "servers" have no `systemd`; `sshd` is the main process. Ansible's `service` module falls back to the old `service`/`/etc/init.d` scripts, which works for nginx and redis. On a real VM you'd use the same playbook unchanged, and it would use systemd.

Also, the servers aren't persistent: `docker compose down` + `up` gives you blank servers again. That's handy for re-running the walkthrough.

### `ansible.cfg` in a world-writable folder is ignored

Files from `/mnt/...` (Windows drives) appear world-writable, and Ansible refuses to load an `ansible.cfg` from such a directory for security. The demo sets `ANSIBLE_CONFIG=/ansible/ansible.cfg` explicitly in `docker-compose.yml` to avoid that.

### `host_key_checking = False` is for the demo only

Rebuilt containers get new SSH host keys, so checking would fail every time. On real servers keep it on, because it protects you from connecting to an impostor.

## Terraform + Ansible together

```
terraform apply              →  3 empty VMs exist          (provisioning/)
ansible-playbook site.yml    →  they become web + db       (configuration/)
```

Terraform can output the new servers' IPs, and those become Ansible's inventory.

## Handy commands

```bash
ansible-inventory --graph                   # show groups and hosts
ansible all -m ping                         # can I reach everything?
ansible-playbook site.yml --syntax-check    # YAML / structure check
ansible-playbook site.yml --list-tasks      # what would run, in order
ansible-playbook site.yml --check --diff    # dry run with file diffs
ansible-playbook site.yml -v                # more output (-vvv for SSH debugging)
ansible-doc apt                             # docs for a module, offline
```
